# Пятничный футбольный бот

Telegram-бот открывает запись на пятничный футбол, ведёт основной состав и резерв, формирует команды, считает победы и публикует итоговый рейтинг. Запись открывается автоматически во вторник после 10:00 по Москве, бот напоминает о ней со среды по пятницу и закрывает её в пятницу в 20:55. Участники используют inline-кнопки; текстовые `+`, `+1`, `+2`, `-`, `-1`, `-2` служат запасным способом записи.

## Команды администратора

- `/setup` — привязать бота к текущей группе и создать рабочие сообщения;
- `/status` — показать состояние сессии, очереди и следующего действия;
- `/open` — открыть запись вручную;
- `/close` — закрыть запись и сформировать команды;
- `/undo` — отменить последнюю засчитанную победу;
- `/finish` — запросить подтверждение завершения вечера и публикации итогов.

## Что потребуется

- Node.js 22 и npm;
- установленная и инициализированная `yc` CLI с выбранным `folder-id`;
- активный платёжный аккаунт Yandex Cloud;
- **новый** токен от BotFather: ранее опубликованный токен необходимо отозвать до установки webhook;
- числовой Telegram ID каждого администратора.

В BotFather выполните `/setprivacy`, выберите бота и нажмите **Disable**. Это необходимо только для распознавания групповых текстов `+`, `+1`, `+2`, `-`, `-1`, `-2`. Inline-кнопки работают независимо от режима privacy.

## Проверка перед развёртыванием

Основной quality gate выполняется так:

```powershell
npm.cmd ci
npm.cmd test
npm.cmd run test:coverage
npm.cmd run typecheck
npm.cmd run build
```

Порог покрытия относится к детерминированному ядру: конфигурации, безопасному логированию и редактированию секретов, доменным правилам, прикладным сценариям и Telegram-рендерингу. Он намеренно не выдаёт внешний I/O за unit-покрытие: YDB-адаптер, сетевой Telegram-клиент, обработчик Cloud Function и deploy/webhook-скрипты проверяются отдельными контрактными тестами и боевыми пробами.

```powershell
npm.cmd test -- tests/handler.test.ts tests/telegram/client.test.ts tests/scripts/deploy.test.ts tests/scripts/set-webhook.test.ts

# Для отдельной локальной/тестовой YDB, которую разрешено очищать:
$env:YDB_TEST_CONNECTION_STRING = 'grpc://localhost:2136/local'
$env:YDB_ANONYMOUS_CREDENTIALS = '1'
npm.cmd test -- tests/integration/ydb-store.test.ts
Remove-Item Env:YDB_TEST_CONNECTION_STRING, Env:YDB_ANONYMOUS_CREDENTIALS
```

Финальная проверка реального entrypoint выполняется `./scripts/deploy.ps1`: до переключения `stable` скрипт применяет миграцию и проверяет candidate-запросами ответы 403 с неверным секретом и 200 с верным.

## Развёртывание

Откройте PowerShell в корне репозитория и задайте секреты только для текущего процесса:

```powershell
$env:BOT_TOKEN = '<новый токен BotFather>'
$secretBytes = [byte[]]::new(32)
$random = [Security.Cryptography.RandomNumberGenerator]::Create()
try { $random.GetBytes($secretBytes) } finally { $random.Dispose() }
$env:WEBHOOK_SECRET = [Convert]::ToBase64String($secretBytes).TrimEnd('=').Replace('+', '_').Replace('/', '-')
$env:ADMIN_IDS = '123456789,987654321'
```

Несколько ID вводятся именно через запятую. Deploy-скрипт проверяет, что ни один ID не потерян, и внутри environment map заменяет разделитель на `;`; runtime-конфиг принимает оба формата.

Проверьте выбранный каталог и запустите идемпотентное развёртывание:

```powershell
yc config get folder-id
./scripts/deploy.ps1
```

Скрипт создаёт отсутствующие ресурсы, приводит существующую YDB к serverless-конфигурации без provisioned RCU, с лимитом 1 ГБ и защитой от удаления, а затем повторно проверяет эти поля. Если конфигурацию нельзя безопасно обновить или подтвердить, deploy останавливается до создания новой версии. Далее он обновляет существующий минутный таймер до точной конфигурации `stable`, применяет миграцию YDB, проверяет candidate двумя закрытыми пробами и только затем переключает `stable`. Telegram webhook и таймер всегда указывают на `stable`; создание новой `$latest` версии само по себе production не меняет.

После успешного запуска:

1. Добавьте бота в нужную группу.
2. Дайте ему право закреплять сообщения.
3. От имени пользователя из `ADMIN_IDS` отправьте `/setup`.
4. Затем отправьте `/status` и проверьте состояние и следующее действие.

## Откат

Скрипт показывает `Previous stable version ID` и точную команду отката **до** переключения `stable`; если после переключения произойдёт ошибка, он напечатает их повторно. При первом deploy явно сообщается, что предыдущей версии нет. Сохраните ID. Для отката переместите только тег:

```powershell
$PreviousStableVersionId = '<ID из вывода deploy.ps1>'
yc serverless function version set-tag --id $PreviousStableVersionId --tag stable
```

Webhook Telegram, таймер и YDB менять не нужно: они продолжат обращаться к `stable`, а данные останутся в той же базе.

## Резервные копии, мониторинг и бюджет

У serverless YDB автоматические копии входят в бесплатный пакет: две полные копии базы за последние два дня. После первого развёртывания откройте YDB → **Резервные копии** и убедитесь, что они появляются; периодически проверяйте возможность восстановления.

Небольшая группа обычно укладывается в ежемесячный бесплатный пакет: 1 000 000 вызовов Cloud Functions, 10 ГБ×ч выполнения, 1 000 000 RU YDB, 1 ГБ данных YDB и автоматические двухдневные копии. Это предположение, а не гарантия: лимиты общие для всего платёжного аккаунта, после их превышения вызовы, хранение, логи и исходящий трафик тарифицируются. Сверяйте актуальные условия в [описании free tier](https://yandex.cloud/ru/docs/billing/concepts/serverless-free-tier).

Чек-лист ограничения расходов:

- в Billing создайте месячный бюджет «К оплате» на **10 ₽**;
- добавьте уведомления на 50%, 80% и 100% и укажите действующих получателей;
- еженедельно смотрите число вызовов, ошибки и длительность функции;
- контролируйте RU, объём данных и резервные копии YDB;
- проверяйте объём Cloud Logging и исходящий трафик;
- при неожиданном росте расходов вручную остановите таймер или удалите публичный webhook до выяснения причины.

**Бюджет только уведомляет и не останавливает ресурсы или списания автоматически.** Достижение 10 ₽ не является жёстким лимитом.

## Диагностика

- **Webhook не устанавливается.** Проверьте, что токен новый, `WEBHOOK_SECRET` не короче 16 символов, версия `stable` активна, а `FUNCTION_URL` заканчивается на `?tag=stable`. Запустите `node scripts/set-webhook.mjs` в том же PowerShell-процессе и проверьте логи функции, не копируя в них токен.
- **Сообщение не закрепляется.** Выдайте боту право закреплять сообщения в группе и повторите `/setup` от администратора.
- **Автоматическое действие задержалось.** Таймер работает раз в минуту; подождите две минуты, затем выполните `/status`, проверьте состояние триггера и ошибки функции. Время расписания — `Europe/Moscow`.
- **Повторные callback-события.** Бот дедуплицирует Telegram `update_id`; старые кнопки должны отвечать, что действие неактуально. Убедитесь, что настроен ровно один webhook на URL `stable`, не запускайте второй экземпляр бота и проверьте ошибки YDB/функции.
